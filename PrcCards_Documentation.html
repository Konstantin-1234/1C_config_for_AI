1. Общее описание и назначение

Конфигурация предназначена для гибкого управления наборами данных (карточками) с динамической структурой реквизитов. Пользователь определяет виды карточек, задает список доступных реквизитов и их стартовые значения. Затем создаются экземпляры карточек, значения которых хранятся в регистре сведений. Изменение реквизитов может происходить вручную или автоматически через систему правил (условия → действия), привязанных к командам.

Ключевая особенность — исполняемый движок правил, который позволяет создавать кнопки команд на форме карточки. При нажатии проверяются сложные условия (включая интервалы) по текущим значениям реквизитов, и если условия выполнены, значения обновляются.

5. Бизнес-логика и механизм правил

🔄 Алгоритм проверки условий

Логика определения того, должно ли сработать правило, строится на четырехуровневой иерархии условий. Правило считается выполненным, если истинно хотя бы одно из условий верхнего уровня.

  1. Уровень правила (ИЛИ между группами):
    Правило применяется, если выполняется условие хотя бы в одной из Групп табличной части Условия. Группы работают как альтернативные сценарии (логическое ИЛИ).
  2. Уровень группы (И внутри группы):
    Условие конкретной группы считается выполненным, если выполнены условия по всем видам реквизитов, указанным в строках этой группы. Это обеспечивает комплексную проверку состояния карточки (логическое И).
  3. Уровень вида реквизита (ИЛИ внутри вида):
    Условие по конкретному виду реквизита считается выполненным, если выполнено хотя бы одно из условий, описанных в строках, относящихся к этому виду реквизита в данной группе. Это позволяет задавать несколько вариантов значений для одного параметра.
  4. Уровень строки (И внутри строки):
    Условие в отдельной строке считается выполненным, если истинны оба внутренних сравнения (Сравнение_1 и Сравнение_2).
    Примечание: Двойное условие в строке предназначено для проверки попадания значения в интервал (например: Значение > 100 И Значение < 200). Если второе сравнение имеет значение НеИспользовать, проверяется только первое.

🚀 Инициализация и выполнение команд

Инициализация карточки:

  1. При записи новой карточки вызывается СтартоватьКарточку.
  2. Система читает ТЧ Реквизиты из ВидаКарточки.
  3. Для каждой строки проверяется поле Действие:
    • Установить -> Берется значение из СтартовоеЗначениеРеквизита.
    • ТекущаяДата -> Устанавливается ТекущаяДатаСеанса().
    • НеИзменять -> Пропускается.
  4. Создается документ _ДвиженияКарточки, заполняется его ТЧ Реквизиты и документ проводится.

Выполнение команд (Правила):

  1. На форме карточки динамически формируются кнопки на основании _ВидыКарточек.ОтображаемыеГруппыКоманд.
  2. При клике вызывается серверный метод _Команды.ВыполнитьКоманду.
  3. Вызывается _Правила.ПолучитьДоступныеПравила, который через сложные запросы с временными таблицами фильтрует правила, удовлетворяющие Алгоритму проверки условий.
  4. Если найдено одно правило с обработчиком СтандартнаяОбработка:
    • Создается документ _ДвиженияКарточки.
    • На основании ТЧ Действия правила напрямую заполняется набор записей регистра Движения._РеквизитыКарточек (минуя ТЧ документа).
    • Движения записываются, документ проводится.

⚠️ Особенности реализации:

  1. В документе _ДвиженияКарточки отключено автоудаление движений при отмене проведения (AutoDeleteOff).
  2. В перечислении _ВариантыСравнения удалено значение "Между", так как интервалы теперь реализуются через пару полей Сравнение_1 и Сравнение_2.
  3. Команды группируются через новый справочник _КомандыГруппы.

6. Анализ реализованного кода

  • Catalog._Карточки.ObjectModule: Реализована логика СтартоватьКарточку с использованием справочника _Действия.
  • Catalog._Карточки.Form.ФормаЭлемента.Module: Реализовано динамическое создание кнопок команд на форме и их группировка. Используется клиент-серверный вызов через общие модули.
  • Catalog._Команды.ManagerModule: Центральный узел выполнения. Координирует поиск правил и вызов обработчика. Создает документы движений при стандартной обработке.
  • Catalog._Правила.ManagerModule: Содержит сложную логику выборки правил. Использует МенеджерВременныхТаблиц для объединения данных о состоянии карточки и условиях правил, реализуя 4-уровневую логику проверки (Группа/Атрибут/Строка/Сравнение).
  • CommonModule._КомандыКлиент/ВызовСервера: Обеспечивают безопасный переход контекста Клиент -> Сервер при нажатии кнопок.
  • Document._ДвиженияКарточки.ObjectModule: Стандартная ОбработкаПроведения переносит данные из ТЧ "Реквизиты" в регистр. (Используется при инициализации, но не при выполнении команд).

Внимание ИИ: При получении задач на доработку этой конфигурации руководствуйся следующими правилами:

🛠️ Технические ограничения и стиль

  • Платформа: 1С 8.3.27. Используй современный синтаксис (Управляемое приложение, клиент-серверное разделение).
  • Именование: Сохраняй префикс _ для всех объектов. Используй понятные имена на русском.
  • Хранение данных: Никогда не добавляй статические реквизиты в _Карточки для хранения игровых/динамических параметров. Всегда используй регистр _РеквизитыКарточек.
  • Типы данных: В правилах сравнения (ТЧ Условия) теперь строго используются перечисления _ВариантыСравнения, а не строки. Не используй строковые значения "Равно" и т.д.

📦 Паттерны реализации

  • Инициализация: Используй механизм СтартоватьКарточку с проверкой поля Действие в шаблоне вида карточки.
  • Команды: Новые команды должны добавляться в справочник _Команды с указанием Группы. Для отображения на форме вид карточки должен ссылаться на эту группу в ТЧ ОтображаемыеГруппыКоманд.
  • Правила: При создании правил используй два поля сравнения для интервалов. Если нужен интервал, в Сравнение_1 ставь "Больше/Равно", в Сравнение_2 — "Меньше/Равно".
  • Запись данных:
    • При старте карточки -> Заполняй ТЧ документа Реквизиты.
    • При выполнении правил -> Заполняй набор записей Движения._РеквизитыКарточек напрямую в модуле менеджера команд.
